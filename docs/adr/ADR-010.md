# ADR-010 — Cliente HTTP, escalera de timeouts, mapeo de errores y evolución del contrato

| Campo | Valor |
|---|---|
| Estado | Borrador (W0.10). H6 aprobada para diseño; H12 adoptada |
| Implementa | SAPI-57, SAPI-61, contrato v0.2 (W1) |
| Relacionado | ADR-005, ADR-007 |

## Decisión
1. **Cliente.** El backend llama al servicio ML con `RestClient`
   (`spring-boot-starter-restclient`, gestionado por el BOM 4.1.1). Es el
   sucesor síncrono de `RestTemplate`; ver la nota de coherencia de
   SAPI-57.CA1 en `docs/hito2/requerimientos-sprint2.md`. **Daniel aprobó
   `RestClient` como implementación de SAPI-57.CA1 (2026-10-10)**: cumple el
   mismo objetivo arquitectónico que WebClient o RestTemplate (Spring consume
   FastAPI por HTTP, desacoplado, con timeouts y errores controlados, contrato
   y pruebas reproducibles). No se reemplaza por otra API solo por la
   redacción histórica de Jira.
2. **Passthrough.** El backend valida las invariantes del contrato y reenvía
   los bytes del cuerpo del ML. No lo mapea a clases que descarten campos
   desconocidos, así que los campos aditivos de v0.2 pasan sin cambios en el
   backend.
3. **Escalera de timeouts** (valores iniciales; W0.2 mide la latencia real en
   contenedor): scoring ML ~14 s (medición informal) < lectura backend→ML
   60 s < lectura Streamlit→backend 90 s. Conexión: 2 s.
4. **Mapeo de errores del backend:**

| Situación | HTTP | `error_type` |
|---|---|---|
| `forecast_time` inválido (el ML no se llama) | 422 | `invalid_request` |
| El ML responde algo que no cumple el contrato | 502 | `upstream_invalid_response` |
| El ML no puede puntuar (503 propagado) | 503 | `prototype_unavailable` / `data_unavailable` |
| El ML no es accesible | 503 | `upstream_unavailable` |
| El ML no responde a tiempo | 504 | `upstream_timeout` |
| Error inesperado o falla de persistencia | 500 | `internal_error` |

**Implementación (SAPI-57, en revisión).** Los casos que la tabla no detallaba
quedaron así:
- **Cliente HTTP:** el del JDK en HTTP/1.1, sin seguir redirecciones.
- **Timeouts:**
  - de conexión, `SAPI_ML_CONNECT_TIMEOUT` (2 s);
  - de lectura, `SAPI_ML_READ_TIMEOUT` (60 s). Con el cliente del JDK es un
    plazo total, desde el envío hasta el último byte del cuerpo.
  - Un número sin unidad se lee en segundos.
  - Un timeout de conexión, de espera de headers o a mitad del cuerpo → 504
    `upstream_timeout`.
  - Un corte de conexión antes del plazo → 503 `upstream_unavailable`.
- **Entrada:** `forecast_time` debe ser RFC 3339 con zona horaria; si no,
  422 sin llamar al ML.
  - Se exigen los segundos.
  - Se rechazan `-00:00` y los segundos intercalares.
  - El offset se limita a ±18:00.
  - Un parámetro que Tomcat no puede decodificar (por ejemplo `%ZZ`,
    `InvalidParameterException`) también da 422 `invalid_request`. Es una
    dependencia de Tomcat embebido.
- **Errores del ML:**
  - Un cuerpo mayor a 1 MiB → 502 `upstream_invalid_response`, con cualquier
    código. El stream se cierra sin esperar el resto.
  - 200 que no cumple `RankingResult` (incluido un cuerpo que no es un
    objeto JSON en UTF-8) → 502 `upstream_invalid_response`.
  - 422 con cuerpo `Error` `invalid_request`:
    - si el backend envió `forecast_time` → 422 `invalid_request` (el ML
      rechazó un `forecast_time` que el backend aceptó);
    - si no lo envió → 502 `upstream_invalid_response`.
  - 422 sin ese cuerpo → 502 `upstream_invalid_response`.
  - 500 → 500 `internal_error`.
  - 503 con otro cuerpo o con un `error_type` desconocido → 503
    `upstream_unavailable`.
  - Cualquier otro código, incluidas las redirecciones → 502
    `upstream_invalid_response`.
- **Mensajes:** son fijos por `error_type`; nunca se reenvía el texto del ML.
- **Correlación:** cada respuesta del handler de `GET /api/v1/ranking` lleva
  `X-Request-Id` (el recibido si es seguro, o uno generado), que también se
  envía al ML. Las respuestas que Spring genera antes del handler (405, 406,
  404) quedan fuera del contrato.
- **Log `ml_predict`:** exactamente uno por llamada al ML, sin scores ni celdas.
  - Campos: `request_id`, `ml_responded`, `ml_http_status` (solo si llegó la
    línea de estado), `ml_latency_ms` (solo la llamada al ML), `outcome`,
    `backend_http_status`, la trazabilidad del ranking y `violation` cuando
    corresponde.
  - Un error inesperado sale en nivel ERROR con `error_class` y la causa, y la
    respuesta es 500 `internal_error`.
- **Riesgo conocido:** Spring atiende `HEAD /api/v1/ranking` con el mismo
  handler, así que también ejecuta un scoring completo.

5. **Contrato v0.2, aditivo.** Campos opcionales planos con los nombres de
   `sapi-output-v1` (`weather_timestamp`, `freshness`, `firms_origin`,
   `firms_coverage_end`, `firms_lag_days`, `firms_status`, `station_id`,
   `station_name`), `GET /api/v1/ranking/latest` y headers opcionales. Se sube
   `info.version` y `schema_version` no cambia. No se exponen meteorología ni
   features por celda. El servicio ML emite los campos agregándolos como
   opcionales a `RankingResult`; `scripts/freeze_check.py` (F4c) acepta
   campos nuevos en esa clase y falla si se altera uno existente.
6. **Acoplamiento `ml_api` → `tools.n8n_bridge.contract`.** Se mantiene
   durante el Hito 2: el validador está en un archivo hasheado por readiness
   y moverlo invalidaría la evidencia de SAPI-71/72. Se refactoriza después
   del Hito 2, con un re-baseline coordinado.
