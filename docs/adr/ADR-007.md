# ADR-007 — Ranking write-through en el backend, consulta `/latest` y Spring Boot como único escritor

| Campo | Valor |
|---|---|
| Estado | Borrador (Quality Gate W0.10, 2026-10-08). Decisiones H2, H5 y H10 aprobadas en GO W0 |
| Implementa | SAPI-57, SAPI-59 (W1) |
| Relacionado | ADR-001, ADR-003, ADR-005, ADR-010 |

## Contexto
`backend.v0.yaml` (L44-49) define `GET /api/v1/ranking` como una llamada al
servicio ML que devuelve el resultado "tal cual". SAPI-59 exige además
persistir cada ejecución, consultar el último ranking en menos de 1 s e
insertar de forma idempotente. El freeze (§3) asigna a Spring Boot el registro
de cada solicitud de scoring, pero `ejecuciones` (V002) solo puede guardar
evaluaciones exitosas: sus columnas son NOT NULL y su clave natural colapsa
solicitudes idénticas.

## Decisión
1. **Write-through.** `GET /api/v1/ranking` valida `forecast_time`, llama a
   `POST /predict`, verifica las invariantes del contrato, persiste la
   evaluación en una transacción y devuelve el cuerpo del ML sin reordenar
   ni reformatear.
2. **Idempotencia.** La inserción usa la clave natural
   `ejecuciones_clave_natural (forecast_time, model_version, inputs_fingerprint)`
   con `ON CONFLICT DO NOTHING`; repetir la misma evaluación no crea filas
   nuevas.
3. **`GET /api/v1/ranking/latest`** (aditivo, contrato v0.2): lee de la base
   el último ranking persistido. Es el modo degradado cuando el servicio ML no
   responde.
4. **Único escritor.** Solo Spring Boot escribe en la base. El servicio ML
   sigue sin persistir nada (`services/ml_api/main.py:14`).
5. **Fail-closed.** Si falla la persistencia del ranking, el backend responde
   500: todo ranking servido queda persistido y trazable.
6. **Auditoría por solicitud (V004 `solicitudes_ranking`).** Una fila por
   request, incluidas las fallidas (código HTTP, `error_type`, latencias,
   `ejecucion_id` cuando existe). Es best-effort: un error de auditoría se
   registra en el log y no cambia la respuesta. Se persiste solo procedencia
   determinista de los insumos; nunca `freshness` ni `age`, que dependen del
   reloj.

## Alternativas
- Read-model batch (Ruta C): requiere contrato v1. Se reconsidera solo si el
  scoring en contenedor supera largamente 60 s.
- Cache por `forecast_time`: rechazado, porque los insumos pueden cambiar
  para el mismo T.
- Auditoría solo con `ejecuciones` y logs: es el fallback si el calendario
  obliga a recortar V004 (primer candidato a simplificar, H5).

## Consecuencias
Cada request en vivo cuesta un scoring completo (~14 s medidos de forma
informal en proceso; W0.2 mide en contenedor). La UI usa `/latest` como
respaldo y los timeouts se escalonan (ADR-010).
